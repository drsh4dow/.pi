### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Verify each PR independently before it lands.** One verifier per PR, each a delegate in its own git worktree, runs the change the way a user would with the matching verification skill (the project's own, see the **create-verification-skill** skill, or the **agent-browser** skill for a browser surface with none), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`, or, on a shared branch, without its approval or with anything outstanding. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land the run bottom-up in one merge.** Run `gh stack merge <ceiling-pr> --yes --squash`, which merges every PR up to and including the ceiling into trunk, all or nothing. A PR outside a stack lands with `gh pr merge <pr> --squash`, and a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm `--auto` (GitHub auto-merge) only on a PR whose verdict covers its current head, because it lands whatever head is ready. After a merge lands, move the PRs above the ceiling onto the merge result with `gh stack rebase` and push them with `gh stack push`. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the PRs above the ceiling is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Re-read the current PR with `gh pr view <pr> --json state,mergedAt,baseRefName` each time a `watch` on `gh pr checks <pr> --watch` returns, until the ceiling reads merged. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling, then dogfood what landed.** Drive the live deployment the way a user would, in staging and in prod. Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, what the dogfood showed, and what the next gap needs.
